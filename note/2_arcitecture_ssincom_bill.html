1ภาพรวมระบบ (System Overview)

ระบบเว็บสำหรับออกและจัดการเอกสารการขายครบวงจร ใช้งานภายในบริษัท (ผู้ใช้บัญชีเดียว) ธุรกิจเกี่ยวข้องกับการขายและขนส่งสินค้า — ใบกำกับแต่ละใบผูกทะเบียนรถและพนักงานขับรถได้ เอกสารธุรกิจ 4 ชนิดเชื่อมโยงกันดังนี้

ความเชื่อมโยงของเอกสารทั้ง 4 ชนิด — ทุกอย่างตั้งต้นจากใบกำกับภาษี

4ระบบยืนยันตัวตนและ Session (Auth & Session)

  • บัญชีผู้ใช้เดียว — POST /login เทียบกับ env APP_USER/APP_PASS (default ในโค้ด: admin/1234) ไม่มีตารางผู้ใช้ ไม่มีการ hash รหัสผ่าน (main.py:41–48)
  • สำเร็จ → เก็บ {"name": username} ใน session cookie (ลงลายเซ็นด้วย SESSION_SECRET, อายุ 2 ชม.) → redirect ไป next (default /dashboard)
  • GET /logout → session.clear() → กลับหน้า login

⚠️ Quirk สำคัญที่สุดของระบบ: invoice_items.invoice_number เก็บค่า idx
ตอนบันทึกใบกำกับ (form.py:232 และ PUT ที่ form.py:379) โค้ดใส่ InvoiceItem.invoice_number = inv.idx — เลข PK จำนวนเต็มถูกเก็บลงคอลัมน์ varchar ที่ควรเก็บ "เลขที่ใบกำกับ" ผลที่ตามมา:
  • relationship Invoice.items (join ด้วยเลขที่ใบ, viewonly) มองไม่เห็นแถวลูกจริง — แทบไม่ถูกใช้
  • ทุก query ต้อง join เผื่อสองแบบ: OR(items.invoice_number = invoices.invoice_number, items.invoice_number = CAST(invoices.idx AS VARCHAR)) — พบใน summary_invoices, bill_note, saletax_report, drivers_form
  • credit_note ใช้ raw SQL inv.idx::text = it.invoice_number
  • ข้อยกเว้น: /api/driver-summary join ด้วยเลขที่ใบอย่างเดียว — ไม่สอดคล้องกับจุดอื่น

รูปแบบเลขเอกสาร (Running Numbers) — ทุกตัวใช้ LIKE + max ไม่ใช่ DB sequence, ปีเป็น พ.ศ.

  • ตรรกะลดหนี้/บรรทัด: ราคาเดิม = price_after_fine + fine, ราคาใหม่ = price_after_fine → มูลค่าลด = Σ max(0, (เดิม−ใหม่)×จำนวน) + VAT 7% · เอกสาร 10 บรรทัด/หน้า

9Flow ความเชื่อมโยงแบบ End-to-End

เส้นทางหลัก: ฟอร์ม → บันทึกลง ss_invoices → PDF · แตกแขนงไปใบวางบิล / ใบลดหนี้ / รายงาน

(a) เข้าสู่ระบบ

Browser: GET /login → กรอกฟอร์ม → login.js POST /login
main.py: เทียบ APP_USER/APP_PASS → ตั้ง session cookie → 303 ไป /dashboard
dashboard: เช็ค session (หน้าเดียวที่เช็ค) → แสดงเมนูไปทุกโมดูล

(b) สร้างใบกำกับภาษี → Export PDF 4 ชุด

/form (form.html + form.js)
  1. เปิดหน้า: fetch ลูกค้า /api/customers/all|suggest, สินค้า /api/products/all,
     คนขับ /api/drivers, ทะเบียนรถ /api/suggest/number_plate
  2. เลือกลูกค้า → autofill ที่อยู่/taxid/เครดิตวัน (จาก /api/customers/detail)
  3. กรอกเลขที่ใบกำกับ → /api/invoices/check-number กันซ้ำ
  4. [พรีวิว]  POST /preview → ได้ HTML invoice.html เปิดดูก่อนบันทึก
  5. [บันทึก]  POST /submit
        → INSERT ss_invoices.invoices (พร้อม snapshot ลูกค้า + car/driver)
        → INSERT ss_invoices.invoice_items (⚠ invoice_number = idx)
        → due_date = invoice_date + เครดิตวัน
  6. [PDF]    POST /export-merged-pdf
        → invoice.html × {ใบกำกับ,ใบเสร็จ} × {ต้นฉบับ,สำเนา} → WeasyPrint → pypdf merge
  (โหมดแก้ไข: /form?edit={idx} → GET /api/invoices/{idx}/detail → PUT /api/invoices/{idx})

(c) สร้างใบวางบิล

/bill_note.html (bill_note.js)
  1. เลือกลูกค้า (/api/customers/all) + ช่วงวันที่
  2. GET /api/billing-note-invoices
        → ใบกำกับของลูกค้าที่ "ยังไม่เคยถูกวางบิล"
          (กรองด้วยเลขใบกำกับทั้งหมดที่มีใน ss_bills.bill_note_item)
        → ยอดต่อใบ = SUM(items) + VAT 7%
  3. ติ๊กเลือกใบกำกับ → POST /api/billing-notes
        → gen เลข BNTS<ปี><เดือน><run6>
        → INSERT bill_note (snapshot ลูกค้า) + bill_note_item (snapshot ยอดต่อใบ)
        → payment_duedate = วันที่ใบกำกับล่าสุดที่เลือก
        → 409 ถ้าใบกำกับใดถูกวางบิลแล้ว (duplicate guard)
  4. พิมพ์: พรีวิวกรอบ A4 ในหน้า → window.print (ไม่ผ่าน server)

(d) สร้างใบลดหนี้ (อ้างอิง GRN)

/credit_note_form.html (credit_note.js)
  1. ค้นลูกค้า (/api/customers/suggest-*) หรือกรอก GRN → /api/grn/suggest
  2. GET /api/grn/summary → รวมรายการสินค้าที่เคยออกใบกำกับใน GRN นั้น
     (raw SQL join ss_invoices: idx::text = invoice_number)
     + /api/products/price → ราคาขายล่าสุดของสินค้า
  3. กรอกค่าปรับ/ราคาใหม่ → มูลค่าลด = Σ(ราคาเดิม−ราคาใหม่)×จำนวน + VAT 7%
  4. GET /api/credit-notes/generate-number/ → เลข SSCR<run>-<วันเดือน>/<ปีพ.ศ.>
  5. POST /api/credit-notes → INSERT credits.credit_note + credit_note_item
  6. พรีวิว: POST /api/credit-notes/preview · PDF: POST /export-creditnote-pdf

(e) รายงาน (อ่านอย่างเดียว — ทุกตัวคำนวณจาก invoices + invoice_items)

summary_invoices.html → /api/invoices/summary + /api/invoices    (สรุป/รายการ + Excel ฝั่ง browser)
saletax_report.html   → /api/saletax/list                         (ภาษีขายรายใบ + แปลงตัน + Excel/พิมพ์)
drivers_form.html     → /api/driver-summary + /api/driver-invoices (ยอดต่อคนขับ)
dashboard.html        → /api/invoices (7 วันล่าสุด)
สูตรกลางทุกตัว: มูลค่า = SUM(COALESCE(amount, quantity×price)), VAT = 7%

11ข้อสังเกตสำคัญและจุดที่ควรระวัง (เรียงตามผลกระทบ)

  1. API ทั้งหมดไม่มีการยืนยันตัวตน — session ถูกเช็คเฉพาะ /dashboard; ทุก /api/... (รวมสร้าง/ลบเอกสาร) และ endpoint PDF เรียกตรงได้โดยไม่ login; ค่า default admin/1234 และ SESSION_SECRET fallback ก็ hardcode ในโค้ด
  2. Quirk invoice_items.invoice_number เก็บ idx (หัวข้อ 5) — หนี้ทางเทคนิคที่แพร่ทุกโมดูล; ถ้าจะแก้ต้อง migrate ข้อมูลเก่า + รื้อ OR-join ทั้งหมด; ระวัง /api/driver-summary ที่ join ไม่ครอบสองแบบ
  3. Route ชนกัน 5 จุด (หัวข้อ 3) — โค้ดฝั่ง "ผู้แพ้" ตายทั้งที่ยังอยู่ในไฟล์ ชวนแก้ผิดที่ เช่นแก้ PUT /api/invoices/{id} ต้องแก้ที่ form.py ไม่ใช่ summary_invoices.py
  4. โค้ดซ้ำข้ามโมดูล — get_db() ×9, ตัว parse วันที่ ~6 ไฟล์, VAT 7% ประกาศ 3 ไฟล์ + literal อีก 2, แปลงปี พ.ศ. 4 ไฟล์, Jinja2Templates แยกทุก router — แก้สูตรภาษี/วันที่ต้องไล่ทุกไฟล์
  5. ฟอนต์ PDF ผูกกับ Docker image — ไม่มี @font-face; รันนอก image (เช่น dev บน Windows) ฟอนต์อาจเพี้ยน; TTF ใน static/fonts ไม่ถูกใช้
  6. Dead / legacy code — crud.py ไม่ถูก import และอ้างคอลัมน์ที่ไม่มีจริง; /export-pdf/{id} เขียนไฟล์ /tmp (ใช้บน Windows ไม่ได้) และพึ่ง relationship ที่มองไม่เห็น items; test_script.py เป็นไฟล์ทดลอง; pdfkit/wkhtmltopdf ติดตั้งฟรี
  7. check-duplicate ของลูกค้าเป็น stub — ตอบว่าไม่ซ้ำเสมอ การกันลูกค้าซ้ำยังไม่ทำงานจริง
  8. ผู้ขายในใบลดหนี้ hardcode ใน credit_note.py — เปลี่ยนชื่อ/ที่อยู่/เลขภาษีบริษัทต้องแก้โค้ด
  9. ไม่มี migration tool — โครงสร้างตารางจัดการนอกแอปทั้งหมด (เพิ่มคอลัมน์ต้องแก้ model กับ DB พร้อมกันเอง)
  10. เลขเอกสารแบบ LIKE+max — ถ้าใช้พร้อมกันหลายคนอาจได้เลขซ้ำ (race condition); ปัจจุบันผู้ใช้คนเดียวจึงยังไม่เป็นปัญหา
